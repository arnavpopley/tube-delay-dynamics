---

## 1. What this project is

Two linked research outputs from one dataset:

**Output A — the line ranking (the headline).**
Rank all eleven London Underground lines by how they absorb and recover from
delay: (i) how fast each self-regulates back to even headways, (ii) how much
total downstream delay a given shock generates. Expected punchline: the
best-run lines are the most fragile, because tight running leaves no slack to
absorb shocks into.

**Output B — the forecasting study (the rigour).**
Predict the *error* in TfL's own live arrival predictions, using line-state
variables their model appears to ignore (headway configuration, how trains
ahead are running, recent dwell times). Score by forecast horizon against
their benchmark. The deliverable is the horizon at which TfL's predictions
stop being unbeatable — not a claim of beating them everywhere.

Both run off the same collected dataset. The headway dynamics that produce the
ranking are the feature engine for the forecaster.

**Why this design signals well:** the benchmark is external and adversarial,
predictions are logged before outcomes exist, and ground truth arrives
automatically within minutes. It is structurally the same shape as alpha
research.

---

## 2. Non-negotiables

Break these and the research is invalid, not merely worse.

1. **Point-in-time logging.** Store what TfL said *at the moment we asked*,
   stamped with *our own* clock. Never reconstruct or back-fill a prediction.
   The whole benchmark comparison rests on this.
2. **Never overwrite raw data.** `data/raw/` is append-only and immutable.
   All cleaning produces new files in `data/processed/`.
3. **Log failures explicitly.** A gap in the data must be distinguishable from
   "no trains were running". Failed polls get their own records.
4. **No random train/test splits.** Time-ordered splits only. Observations for
   the same train are highly correlated; block by train or by day.
5. **Ignore horizons under ~2 minutes** in any modelling. Ground-truth
   reconstruction is accurate to roughly ±10s, which swamps the signal there.

## 4. Data schema

### `data/raw/arrivals/YYYY-MM-DD/arrivals_*.jsonl`

One record per train-station prediction per poll.

| field | source | notes |
|---|---|---|
| `request_ts` | ours | UTC, when we sent the request. **The canonical time.** |
| `response_ts` | ours | UTC, when the response landed |
| `poll_id` | ours | groups all records from one poll |
| `timestamp` | TfL | their clock — staleness indicator |
| `timeToLive` | TfL | cache expiry — staleness indicator |
| `vehicleId` | TfL | follow a specific train |
| `naptanId`, `stationName` | TfL | station |
| `lineId`, `direction`, `platformName` | TfL | |
| `destinationName`, `towards` | TfL | service pattern |
| `currentLocation` | TfL | free-text position |
| `timeToStation` | TfL | seconds — **the prediction** |
| `expectedArrival` | TfL | absolute time — **the benchmark** |

### `data/raw/status/` — line status per poll, for disruption context
### `data/raw/failures/` — every failed request, with error reason

## 5. Build phases

Work through these in order. Do not start a phase before the one above it is
verified.

### Phase 0 — get collecting (do this first, today)

- [x] Repo initialised, `.gitignore` excludes `.env` and `data/`
- [x] `collector/tfl_collector.py` running against a real `TFL_APP_KEY`
- [ ] Deployed somewhere always-on (Pi / VPS / spare machine), as a systemd
      service or Docker container with restart-on-failure
- [ ] Verified after 20 minutes: `data/raw/arrivals/` filling, roughly 400–700
      records per poll network-wide
- [ ] A simple health check: alert (or just log loudly) if no successful poll
      in 10 minutes

**Every day this isn't running is a day of data that cannot be recovered.**

A live poll of all 11 lines typically returns ~1.5k–4k *prediction rows*
(one per train–station pair TfL currently publishes), not 400–700. Unique
vehicles are usually a few hundred. Treat the 400–700 figure as a sanity
floor, not a ceiling; the quality report prints both counts.

### Phase 1 — ingestion and sanity (day 2)

- [x] `src/ingest.py`: compact hourly JSONL into daily Parquet, partitioned by
      date and line. Use DuckDB for querying.
- [x] Data quality report: polls per hour, records per poll, gaps, failure rate,
      distinct vehicles per line per day
- [ ] **Manual check:** pull 20 individual `(vehicleId, naptanId)` sequences,
      sort by `request_ts`, confirm `timeToStation` decays sensibly to zero.
      Eyeball them. This determines whether the dataset is usable at all.

`python src/ingest.py sequences` dumps 20 such series for that eyeball check.
It does not estimate arrival times.

### Phase 2 — ground truth reconstruction (week 1)

The hardest correctness problem in the project. There is no "train arrived"
event; it must be inferred.

- [ ] `src/reconstruct.py`: for each `(vehicleId, naptanId)` sequence, fit a
      line through the final 3–5 `(request_ts, timeToStation)` points and solve
      for `timeToStation = 0`. That is the estimated arrival.
- [ ] Cross-check against the disappearance window (last poll where present →
      first poll where absent). Flag and drop disagreements.
- [ ] Cross-check against the train's first appearance at the next station down
      the line (catches vehicle-ID errors).
- [ ] Handle explicitly: trains vanishing without arriving (cancelled/reversed),
      vehicle-ID reuse, terminus behaviour, `timeToStation` *increasing*
      between polls (normal — TfL revising — and itself interesting data),
      and our own polling gaps.
- [ ] Output: one row per (train, station) arrival with estimated arrival time,
      a confidence flag, and the full prediction history attached.
- [ ] Tests on synthetic sequences with known answers.

### Phase 3 — headways and the line ranking (week 2)

- [ ] `src/headways.py`: per line/direction/station, the time between
      successive trains. This is the core state variable.
- [ ] Fit an Ornstein–Uhlenbeck process to headway deviations per line.
      The reversion speed θ measures **how aggressively that line is
      regulated**, not a law of nature — metro headways are naturally
      *unstable* (bunching), and reversion exists because of ATO and manual
      regulation. Frame it that way in the write-up.
- [ ] `src/rankings.py`: rank all 11 lines by (i) θ, (ii) delay amplification
      (total downstream delay generated per unit of initial shock),
      (iii) empirical recovery time after real disruptions.
- [ ] Deliverable: one table, 11 rows, 3 columns. **The story is in the
      disagreements between the three rankings.**

### Phase 4 — the forecasting study (weeks 3–4)

- [ ] `src/features.py`. Target: `error = actual_arrival − tfl_predicted_arrival`
      (positive = later than promised). Features: horizon, station, line,
      direction, hour-of-day, day-of-week, current headway to the train ahead,
      delay state of the 1–3 trains ahead, recent rolling dwell times at that
      station, trains currently on the line, line status, weather
      (Open-Meteo, free), OU-implied expected reversion.
- [ ] `src/models.py`: baseline = TfL's own prediction (error assumed 0).
      Then a linear model for interpretability and gradient boosting
      (LightGBM) for performance. Also fit quantile models — the error is
      skewed (trains are late more often than early), so predicting a
      distribution is both more honest and more useful.
- [ ] `src/evaluate.py`: **bucket by forecast horizon** (2–3min, 3–5, 5–8,
      8–12, 12+). Walk-forward validation, blocked by day. Report MAE and
      pinball loss vs the benchmark per bucket, per line, per regime
      (peak / off-peak / disrupted).
- [ ] Deliverable: the skill-versus-horizon curve. The finding is **where the
      crossover sits**, not a single accuracy number. "No edge below X minutes"
      is a legitimate and probably more believable result.

### Phase 5 — write-up (weeks 5–6)

- [ ] `run_all.py` regenerates every figure and table from processed data
- [ ] Paper in `paper/`: question, data and collection design, reconstruction
      methodology, line rankings, forecasting results, limitations
- [ ] Limitations must name: ±10s ground-truth precision, cache staleness,
      collection window length, single-city single-mode scope
- [ ] README with one-command reproduction
- [ ] Optional: a live scoreboard page showing model vs countdown board over
      the trailing week. This is the demo that survives a recruiter clicking
      one link.

## 6. Known traps

- **Placeholder vehicle IDs.** Live polls include `vehicleId=000` (and
  occasionally other reused ids) with many parallel predictions. That is
  not a single train. Leave those rows in `data/raw/`; do not treat them
  as a trajectory. `src/ingest.py sequences` omits `000` from the eyeball
  sample for this reason.
- **Cache staleness.** TfL caches responses; "the prediction at time t" may be
  seconds old. `timeToLive` and their `timestamp` tell you how stale. Treat
  lag as a measured quantity, not zero.
- **Correlated observations.** One train-station pair generates many
  predictions at different horizons. Treating them as independent gives
  wildly optimistic confidence intervals.
- **Non-stationarity.** Timetables change; engineering works come and go.
  Walk-forward validation, and expect performance drift — report it.
- **Rate limits.** Registered keys get a generous allowance, but the Line
  endpoint takes comma-separated IDs, so all 11 lines come in ONE request.
  Don't fan out per-line; you gain nothing and burn quota.
- **Measurement noise attenuates results.** Noise in the target biases toward
  finding *no* edge. Any edge found is therefore, if anything, understated —
  worth stating explicitly.

## 7. Conventions

- Python 3.11+, `uv` or venv, pinned `requirements.txt`
- Parquet + DuckDB for anything above ~1M rows; pandas below that
- All timestamps UTC internally; convert to London time only for display
- Type hints on function signatures in `src/`
- Tests for: reconstruction logic, headway computation, feature alignment,
  the train/test splitter (verify no future leakage)
- Commit the collector's config changes — knowing when polling frequency
  changed matters for interpreting the data later
